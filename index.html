XAI

Project Description:

This project addresses a critical bottleneck in human-robot collaboration research: the lack of transparency in robotic decision-making during cooperative tasks. The Neuromotor Control and Learning (NMCL) Lab at the University of Maryland conducts studies using VTEAM, a virtual reality environment where human participants and a simulated humanoid robot (Baxter) take turns solving Rush Hour-style puzzle games of varying difficulty. While the system enables flexible experimental setup, a major limitation is that human participants often struggle to understand why the robot selects certain moves, impairing trust and effective teamwork. To overcome this challenge, we developed an Explainable Artificial Intelligence (XAI) system that enables Baxter to communicate its reasoning through multiple modalities. Our solution extends the existing Unity3D-based VTEAM framework by allowing researchers to configure when and how explanations are delivered—before, during, or after the robot’s actions—and to control the mode of explanation, including text pop-ups, speech output using the ESpeak API, and graphical overlays with directional arrows on the game board. Users can also select the frequency of explanations (every turn, intermittent turns, or on-demand) and the explanation quality (good, neutral, or bad) to support varied experimental conditions. The enhanced interface empowers researchers to systematically study cognitive load, trust dynamics, and user comprehension under different XAI configurations. By making the robot’s decision-making process visible and tunable, our project advances the NMCL lab’s capability to investigate critical questions in cognitive-motor collaboration, laying the foundation for broader applications of explainable robotics in fields such as autonomous driving, aviation, and surgical assistance.

Additional Work Done Over The Summer
The additional work that was done over the summer was done individually and began in late June and ended in early August with the following: (1) new experimental settings, (2) UI/UX improvements and refactorization, (3) enhancements to testing capabilities, and (4) configure new features while preserving core functionality.
  1. New Experimental Settings:
    • Trial-based experiments: The client wanted the option to conduct experiments in a different manner in particular without the contrainsts poised by the default experimental settings. The new trial-based experimental settings would allow the experimenter to set a fixed number of trials for a set of puzzles with the option to set each each puzzle with the following options: the baxter-player turn ratio, who starts first (robot or human), and whether robot assistance will be enabled for the specified puzzle.
    • Extension of XAI Settings: Rather than having the XAI settings be used for the whole experiment the epxerimenter would have the option to apply a different set of XAI settings depending on the puzzle difficulty phase. For example, the experimenter could set the XAI settings to have the robot explanations occur more frequently durring the hard puzzle difficulty phase compared to the easy puzzle difficulty phase.
    • Other parameterizations: Additional settings which enabling robot turns only or human turns only for an experiment, and a preserve turns feature that would keep the turn order across puzzles as by default the turn order count between the robot and player resets after each puzzle.
  2. UI/UX improvements and refactorization:
    • Planning algorithm selection dropdown: Created a dropdown which would allow the experimenter to select between different planning algorithms that were stored in a folder rather than using an absolute path to a specific planning algorithm.
    • Overwrite option for XAI settings: Created a toggle which when enabled would allow the experimenter when setting the default XAI settings to also overwrite the XAI settings for each puzzle difficulty phase.
    • Default experiment file: Created a default experiment file which would be loaded in when the experimenter loads in the experimental settings scene. The default file would be modifiable through the experimental settings scene rather than directly through the file to avoid potential parsing errors with the xml format and the nested structure of some datastructures.
    • Refactorization through modularity: Split code into smaller reusable functional units through the use of C# object oriented approach with class inheritance, utilized UNITY prefabs for re-using UI elements alongside their base functionality, and general code cleanup i.e. more expressive variable names.
  3. Enhancements to testing capabilities:
    • Logging for testing purposes: Implemented with the existing logging system to log information for an experiment that would be useful to trace issues with the runtime system. This was done to assist the experimenter to report issues for an experiment to the current development team to help debug the issues sooner.
  4. Enhanced core features while integrating new functionality:
    • Enhanced audio XAI explanations: Ensured that the audio explanations would prevent the user or robot actions until the audio explanation finished playing in line with the other XAI explanation modes.
    • Improvised various experiment settings and quirks for compatibility with the preserve turns feature: Experimental settings including disengagement period (setting where the robot disengages), who starts (robot or human), and baxter-player ratio were either modified or taken in concideration of implementing the presever turns feature. Furthermore, a quirk was discovered with how the turn counter for the human player was updated where when the player let go of the block it would snap updating the counter. However, if the player did the completing move for a puzzle the block could either snap or be held by the player to the end (completion) location of the puzzle. Thus, to address this hooks were added to the runtime system to detect if the block snapped or not for the final move of the puzzle.

Blog for Geeks

Project Description:

A full-stack personal website utilizing Express.js and JavaScript for the webserver and React for displaying and querying different types of posts, implementing secure login authentication and scalable, query-based CRUD operations for managing posts, blogs, and tickets. Developed a custom ticketing system to track and quantify personal project development velocity with graphs, incorporated GitHub API integration to link tickets directly with recent commits for streamlined work explanation and project transparency, utilized Sass to construct a responsive UI with mobile-first front-end design, and basic optimization and load testing through k6.
